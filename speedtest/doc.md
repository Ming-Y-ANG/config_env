# 网速测试原理与页面参数说明

> 适用项目：基于 [`@cloudflare/speedtest`](https://github.com/cloudflare/speedtest) 测速引擎 + 自建 Node.js（Express）后端的网速测试网站。
>
> 本文档分两部分：**第一部分**讲清测速引擎的工作原理与计算口径；**第二部分**逐项解释页面上每个参数/图表的含义。

---

## 第一部分：测速原理

### 1. 整体架构

```
┌─────────────┐   GET  /__down?bytes=N （下载测量，N 字节数据）
│             │ ──────────────────────────────▶│
│   访客浏览器  │   POST /__up  （上传测量，body 为 N 字节）
│  （测速引擎） │ ◀──────────────────────────────│  你的 VPS
│             │   GET  /__down?bytes=0 （延迟测量，空响应）
└─────────────┘                                └─────────┘
```

- **测速引擎是纯前端 JavaScript**，在访客浏览器中运行，不经过任何中转；VPS 是测量的**对端（终点）**，只负责按请求吐出/接收指定字节数的数据。
- 所有时序数据来自浏览器内置的 **PerformanceResourceTiming API**（资源计时 API），精度可达微秒级。
- 因此测量结果 = **访客浏览器 ↔ 你的 VPS 之间真实链路**的质量，上限受 VPS 自身带宽约束（访客下载速度 ≈ min(访客带宽, VPS 上行带宽)）。

### 2. 测量流程（测量序列）

引擎按预定义序列依次执行测量，采用**从小到大逐步加码（ramp-up）**策略——小文件快速摸底，大文件精确测量。一旦某方向的单个请求时长超过 **1000ms**（`bandwidthFinishRequestDuration`），就认为已测准，跳过该方向更大的文件，避免浪费流量：

| 顺序 | 类型 | 参数 | 目的 |
|---|---|---|---|
| 1 | latency | 1 个包 | 初始延迟估算 |
| 2 | download | 100KB × 1 | 初始下载估算 |
| 3 | latency | 20 个包 | 正式空闲延迟测量 |
| 4 | download | 100KB × 9 | 小文件下载 |
| 5 | download | 1MB × 8 | 加码 |
| 6 | upload | 100KB × 8 | 上传起步 |
| 7 | upload | 1MB × 6 | 加码 |
| 8 | download | 10MB × 6 | 大文件下载 |
| 9 | upload | 10MB × 4 | … |
| 10~15 | 交替加码 | 最大下载 250MB / 上传 50MB | 直到请求时长足够长 |

> 丢包测试（packetLoss）需要通过 WebRTC 向 TURN 服务器发 UDP 包，需自建 TURN 服务器（Cloudflare 公共 TURN 已弃用），**本项目中默认关闭**。

### 3. 延迟（Latency / Ping）与抖动（Jitter）

- **测量方式**：向 `/__down?bytes=0` 发 GET 请求，服务器立即返回空响应。取该请求的 **TTFB（首字节时间）** 作为一次延迟样本：

  ```
  延迟样本 = responseStart − requestStart
  ```

- **最终延迟**：所有空闲延迟样本的**中位数（P50）**，抗个别抖动的干扰。
- **抖动**：相邻两次延迟样本差值的平均（平均绝对偏差），反映延迟的稳定性。视频通话、游戏对抖动尤其敏感。

### 4. 下载 / 上传带宽

**下载**：`GET /__down?bytes=N`，服务器返回 N 字节随机数据。
**上传**：`POST /__up`，body 为 N 字节数据，服务器接收后立即响应。

每次请求得到一个带宽样本：

```
带宽(bps) = 传输比特数 ÷ (请求总时长 − 服务端处理耗时)
```

- 下载的"传输比特数"取浏览器统计的 `transferSize`（线上实际传输字节，含协议开销）× 8；
- 上传按 `发送字节数 × 8 × 1.005`（0.5% 协议开销估算）；
- **最终带宽** = 所有有效样本的 **P90 百分位**（接近峰值但过滤掉个别异常高值）。

**有效样本的门槛**：单个请求时长必须 **≥ 10ms**（`bandwidthMinRequestDuration`）。太短的请求计时误差占比太大，会被丢弃。这也是极速网络（如同机房、千兆以上）下小文件采样可能被判定无效的原因——引擎的 ramp-up 机制会自动用更大的文件兜底。

### 5. 负载延迟（Loaded Latency）

空闲延迟低不代表真实体验好——**拥塞时的延迟**才是关键。引擎在下载/上传大文件的同时，每 400ms 并发发送 `bytes=0` 轻量请求，测量**链路满载状态下的延迟**：

- 参与统计的大文件请求时长需 ≥ 250ms（`loadedRequestMinDuration`）；
- 最多保留最近 20 个样本（`loadedLatencyMaxPoints`）；
- 由此派生 **负载延迟增量 = max(下载负载延迟, 上传负载延迟) − 空闲延迟**，是 AIM 评分的重要输入。

> 若页面显示"负载延迟 --"，表示本次测试负载样本不足（通常因网络极快、大文件瞬间传完），不影响其他结果。

### 6. 服务端耗时扣除（Server-Timing）

请求总时长里包含服务器生成/接收数据的处理时间，不应计入网络传输。后端通过响应头上报：

```
Server-Timing: cfRequestDuration;dur=0.0001
```

引擎从响应头解析该值并从时长中扣除。注意两个口径细节：

- 引擎会**忽略小于 0.01ms 的值**（视为可忽略噪声）——本项目后端即时响应，因此页面上"服务端处理"列显示为 `—`，属正常；
- 未上报时则不做扣除（或使用配置的固定估计值）。

### 7. 跨域与 Timing-Allow-Origin

浏览器安全策略规定：**跨域请求的详细计时分段（requestStart、responseStart、transferSize 等）默认被隐藏为 0**，除非响应携带：

```
Timing-Allow-Origin: *
```

缺失该响应头时，引擎拿不到任何时序数据，速率/延迟会全部计算为 0。本项目后端已返回该头，且页面内置了自动检测（通过检查 PerformanceResourceTiming 条目），缺失时会在页面顶部给出明确警告。同源部署（推荐）天然无此问题。

### 8. AIM 网络质量评分

测试完成后，引擎按 Cloudflare 的 [AIM（Aggregated Internet Measurement）](https://developers.cloudflare.com/fundamentals/speed/aim/) 模型，把原始指标换算成三类典型场景的得分与五档评级：

| 场景 | 输入指标 | 评级阈值（分） |
|---|---|---|
| 🎬 视频流媒体（streaming） | 延迟、丢包、下载带宽、负载延迟增量 | 15 / 20 / 40 / 60 |
| 🎮 在线游戏（gaming） | 延迟、丢包、负载延迟增量 | 5 / 15 / 25 / 30 |
| 🎧 实时通话（rtc） | 延迟、抖动、丢包、负载延迟增量 | 5 / 15 / 25 / 40 |

- 各输入指标先按各自曲线换算成分数并求和，再按阈值映射为五档：**很差 / 较差 / 一般 / 良好 / 极佳**；
- 未启用丢包测试时，丢包项按 0 分计入。

## 第二部分：页面参数含义

### 主速度区（顶部大卡片）

| 元素 | 含义 |
|---|---|
| **大号数字 + Mbps** | 测速中：当前阶段最近一次采样的实时速率；延迟阶段：当前延迟（单位变为 ms）；完成后：最终下载带宽（P90）。若极速网络下汇总值无效，则回退显示采样峰值 |
| **阶段标签**（如"下载测速中"） | 引擎当前所处的测量阶段：延迟测量 → 下载 → 上传 → 完成 |
| **进度条 + 百分比** | 已完成请求数 ÷ 序列总请求数 |
| **开始 / 停止 / 重新测试按钮** | 控制测速引擎的运行 |

### 四项指标卡

| 指标 | 含义 |
|---|---|
| **下载速度**（橙边） | 下行带宽汇总值（P90），单位 Mbps（= bps ÷ 10⁶）。副文案显示采样次数与峰值 |
| **上传速度**（蓝边） | 上行带宽汇总值（P90），同上 |
| **延迟 Ping**（绿边） | 空闲状态往返延迟的中位数，单位 ms。副文案显示 Ping 次数与最小值 |
| **抖动**（黄边） | 空闲抖动（相邻延迟差值的平均），单位 ms。副文案显示负载延迟：`↓` 为下载满载时延迟，`↑` 为上传满载时延迟；样本不足时显示 `--` |

### 实时速率曲线

- 横轴为测试进行的时间（秒），纵轴为速率（Mbps）；
- **橙色曲线**为下载采样点、**蓝色曲线**为上传采样点，按时间顺序连成，端点为最近一次采样；
- 曲线的"爬坡"形态正是 ramp-up 机制的体现：小文件低估 → 大文件逼近真实带宽。

### 数据分析区（测速完成后展开）

**网络质量评分（AIM）**：三类场景各显示评级（很差/较差/一般/良好/极佳）、得分（pts）与比例条。评级越高表示该场景下体验越有保障。

**空闲延迟分布**：每根绿色柱子代表一次 Ping 的延迟值，可直观看出延迟是否平稳；标注中位数与最大值。

**连接信息**：

| 字段 | 来源 |
|---|---|
| 你的 IP / 位置 / ASN / 测速节点 / 时区 | 测速 API 响应的 `cf-meta-*` 头（仅 Cloudflare 官方节点提供；自建后端无此信息时自动隐藏） |
| 测试总耗时 | 引擎实际运行时长（不含暂停） |
| 测速 API | 本次测试实际使用的后端地址 |

**测量点明细表**：每一次下载/上传请求的完整记录，按时间排序：

| 列 | 含义 |
|---|---|
| 方向 | 下载（橙）/ 上传（蓝） |
| 数据大小 | 该次请求的文件大小 |
| 速率 | 该次采样算出的带宽（绿色加粗 = 该方向峰值） |
| 耗时 | 请求总时长（含网络与服务端处理） |
| TTFB | 首字节时间，近似于该次请求的链路延迟 |
| 服务端处理 | 后端上报的 Server-Timing 耗时；`—` 表示未上报或可忽略（<0.01ms） |

### 提示横幅

| 提示 | 触发条件 |
|---|---|
| "正在使用 Cloudflare 官方演示节点" | 页面上线但未检测到同源后端，自动回退到官方节点演示 |
| "未返回 Timing-Allow-Origin" | 跨域后端缺少计时暴露头，测速将无法计算——按提示补响应头即可 |

## "单请求超过 1000ms 就认为测准"的完整运作机制

### 引擎手里的"弹药表"

测量序列里，下载和上传各自准备了一组**按文件大小递增**的弹药：

```plain
下载：100KB → 1MB → 10MB → 25MB → 100MB → 250MB
上传：100KB → 1MB → 10MB → 25MB → 50MB
```

如果没有停止机制，引擎会把整张表全部打出去——慢网用户要硬下载几百 MB，既慢又费流量。

### 停止规则的精确含义

**每完成一个请求，引擎检查一次："这个方向（下载或上传）是否已经出现过一个时长 ≥1000ms 的请求？"**

- 出现了 → 该方向**剩余更大的文件全部跳过**，这个方向宣告测完
- 没出现 → 继续用下一档更大的文件测

注意三个细节：

1. **"某方向"是独立判断的**——下载达标了只停下载，上传继续加码，互不干扰；
2. **停止的是"更大的文件"，不是停止测量**——达标那一档的请求可能已经把计划内的几个都跑完了；
3. **判断发生在每个请求之后**，不是等一整组跑完——一旦某个请求撑满 1 秒，立刻收手。

### 用两个例子看它怎么自适应

**50 Mbps 的家庭宽带用户**：

| 文件                 | 理论耗时   | 判定                  |
| :------------------- | :--------- | :-------------------- |
| 100 KB               | ~16 ms     | 太短，继续            |
| 1 MB                 | ~160 ms    | 不够，继续            |
| **10 MB**            | **~1.6 s** | ✅ **≥1000ms，达标！** |
| 25MB / 100MB / 250MB | —          | 全部跳过              |

**1000 Mbps 的宽带用户**：

| 文件       | 理论耗时 | 判定           |
| :--------- | :------- | :------------- |
| 1 MB       | ~8 ms    | 继续           |
| 10 MB      | ~80 ms   | 继续           |
| 100 MB     | ~800 ms  | 还差一点，继续 |
| **250 MB** | **~2 s** | ✅ 达标，结束   |

看出设计的精妙了吗：**网络越快，用的文件越大；网络越慢，越早收工**——但无论快慢，最终都保证拿到了"至少持续 1 秒"的样本。而 1 秒的意义就是之前讲过的两层：计时噪声被稀释到 ±0.2% 可忽略、TCP 早已穿过慢启动进入稳态。

所以 1000ms 不是"测速总时长"，而是**单个请求的时长门槛**——它同时保证了精度下限和流量上限。

## TURN 测丢包的流程和原理

### 先理解：为什么测丢包不能用 HTTP

这是最根本的问题。你现有的 `__down`/`__up` 全是 HTTP，走的是 **TCP**，而 TCP 有个致命特性：**自动重传**——链路丢了一个包，协议栈会悄悄重发，应用层完全无感知。所以 TCP 测出来的丢包永远是 0%，它只会表现为"速度变慢"，**丢包这个指标在 TCP 层面根本不存在**。

要看到真实丢包，必须发 **UDP**（无连接、无重传，丢了就是丢了）。

但浏览器出于安全限制**不允许网页裸发 UDP 包**——唯一的例外通道是 **WebRTC**（为实时音视频设计的浏览器原生 P2P 框架，底层走 UDP）。所以测丢包必须借道 WebRTC。

### TURN 服务器在这里扮演什么角色

WebRTC 本是 P2P 设计（两个浏览器直连），但现实中设备都在 NAT 后面，很多场景直连不通，于是有了 **TURN（Traversal Using Relays around NAT）**：一台带公网 IP 的中继服务器，客户端连不上对端时，把 UDP 包发给 TURN，由它转发。

测丢包正是利用了这个中继能力，而且用了一个巧妙的结构——**自己连自己**（引擎里叫 `SelfWebRtcDataConnection`）：

```plain
              你的 VPS (coturn)
                    ▲  │
        UDP 探测包   │  │  中继回来
                    │  ▼
   浏览器 [PeerConnection A] ══数据通道══ [PeerConnection B] 浏览器
              （同一个页面里的两个端点）
```

浏览器在同一个页面里创建**两个** WebRTC 端点互连，并且设置 `iceTransportPolicy: 'relay'` **强制禁止直连**——于是每个数据包的真实旅程是：

```plain
浏览器 → （互联网）→ 你的 VPS 的 coturn → （互联网）→ 浏览器
```

**每个包都在"浏览器↔VPS"这段链路上完整跑了两个方向**——这正是我们想知道丢包率的那条路。

### 完整流程（对应你的部署）

```plain
① 浏览器 → GET /turn-creds → 你的 Node 后端
   后端用共享密钥算出临时凭证 {username, credential} 返回
        │
② 浏览器创建 WebRTC 连接，ICE 配置：
   urls: turn:你的VPS:3478 + 凭证 + 强制 relay
        │
③ ICE 协商：浏览器向 coturn 发 Allocate 请求（UDP 3478）
   coturn 验证凭证 → 从 49152-49252 端口池分配一个中继端口
        │
④ 数据通道打通（两个端点都绕道中继，链路成立）
        │
⑤ 正式探测：连发 1000 个带序号的 UDP 包
   每批 10 个、批间隔 10ms（模拟真实语音流的包速）
        │
⑥ 收包对号：每收到一个包，按序号标记"已回收"
        │
⑦ 全部发完后等待 3 秒（responsesWaitTime）：
   · 全部提前收齐 → 立即结束
   · 超时仍有缺口 → 未回收的判定为丢失
        │
⑧ 丢包率 = 丢失包数 ÷ 实发包数
```

### 为什么这个结果可信

- **UDP 无重传**：丢一个就是真丢一个，没有任何协议层帮你掩盖；
- **双向都测到**：每个包走了"去 VPS + 回浏览器"两程，任何一程丢都算数（测的是链路综合丢包）；
- **样本量足够**：1000 个包意味着 0.1% 的统计分辨率——丢 3 个包就是 0.3%，不会被偶然性主导；
- **分批限速发送**：每批 10 个、间隔 10ms，避免瞬间打满缓冲区造成"自己把自己挤丢"的假丢包。

最后闭环到页面上：`丢包率 = 引擎算出的比例 × 100%` 显示在紫色卡片里，同时作为输入进入 AIM 评分（丢包 <1% 得 +10 分，≥50% 扣到 −20 分）——这就是从一颗 coturn 到页面上那个百分数的完整旅程。
